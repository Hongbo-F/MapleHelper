# gamelab

gamelab drives the real game with exact key timelines, records it, and measures what happened. It started as the way MapleHelper's combo timing was measured: which way she jumped and threw, and whether the game ignored a key. A regular attack locks out jumps and attacks for about 730 ms. Quick taps right after takeoff were missed about 6% of the time.

On top of that it hunts on its own: it finds her and the monsters on screen, places them on the map, plans routes and fights, and sweeps a map platform by platform.

## Layers

The code is organized like a self-driving car's stack. Each layer is a package, and a layer only imports the layers below it (`tests/test_architecture.py` checks this).

```
  behavior      what to do next: the hunter (the agent), fights, looting, tours
     |
     +-- attack       which monster, from where, and how                    [pure decisions]
     +-- control      decisions turned into keys: actions, one move, a route; the key player
     +-- motion       motion planning, A to B: physics, routes, chained key timelines   [pure]
     +-- localization where she, the monsters and the drops are on the map (mined map data)
     +-- perception   pixels to what's on screen (no map knowledge)

  ui            the live mini-map window (reads telemetry)
  sim           an offline game: the stack runs against it with no game and no keys
  analysis      measuring combos and her movement in recordings
  shared        paths, screen geometry, left and right (directions), telemetry, the game window
```

| Package | Does | Main pieces | May import |
|---|---|---|---|
| `perception` | Pixels to what's on screen, in half-size screen px | `Eyes` (the only door to pixels): `look` gives an `Observation` (her name tag, HP/MP, the ground under her, her minimap dot, ropes, her EXP number); `monsters`, `items` and `bar` answer questions about a look's frame. `MobDetector`, `LootDetector`, `NameTag`, `LieDetectorSpotter` | shared |
| `localization` | Where things are on the map, in map units | `mapdata` (the map from the game's own data), `pose` (her position from the minimap dot, refined by ropes or her platform's end; the `Camera`), `Scene` (a look placed on the map), `Monster`/`MonsterTrack`/`Tracker` (monsters seen, told apart from look to look, and where they can be next), `Senses` (every look goes through it) | perception |
| `motion` | Getting from A to B | `body` (how the game moves her: the client's movement step by step, from its own Physics.img), `physics` (jumps, falls and walking, measured), `route` (every move between platforms; Dijkstra), `flow` (several moves chained into one key timeline, hopping monsters) | localization |
| `attack` | Which monster, from where, how | `reach` (where a star hits, and what an attack from a jump can pick), `stance` (throw, jump-throw, jump back, step away, close in), `spots` (where to stand to shoot a platform) | perception (monster names), localization, motion |
| `control` | Keys out | `Actions` (her key plans: throws, walking, pick-up, potions, the chair), `Mover` (one move, closed loop), `Navigator` (a route: chains, glances, cut-offs, replans), `client` (plans to the key player), `player` (the key player itself), `alarm` | perception, localization, motion |
| `behavior` | What to do next | `Hunter` (the agent: senses, actions, a looter, her vitals and health), `fight` (`clear`, `kill`, fighting on the way), `Looter` (sweeps, mop-ups, drops remembered), `Tour`, `probe` (the in-game probes of what a star hits, and their scorer) | all of the above |
| `ui` | The mini-map window | `MapView` (draws a state; pure), `State` (the latest record per topic), sources (live, replay, a planned route), `MapWindow` | localization, motion, attack |
| `sim` | An offline game | `World` (her body, monsters, kills, drops), `FakeEyes`, `FakePlayer`, 66 scenarios, golden traces | everything but ui |
| `analysis` | Combo tests and her movement on recordings | `track`, `scroll`, `analyze`, `calibration`, `recordings`, `physics_check` (her tracked movement against the physics models) | perception, motion, control |

How a look becomes keys:

```
Eyes.look -> Observation -> Senses.look -> Scene ─┬─> attack.stance ─────────────> Actions ─┐
   (perception)            (localization)         └─> motion.route / flow -> Navigator / Mover ─┴─> client -> player -> the game
                                         after each look: the hunter's vitals (EXP gains, HP) and telemetry
```

The loops live in `behavior/fight.py` (a fight), `control/navigator.py` (a route) and `behavior/tour.py` (a sweep).

## How the keys get to the game

MapleStory runs as administrator, and Windows blocks key presses from normal programs into admin windows. So one small process, the **player** (`control/player.py`), runs elevated, and everything else runs normally and talks to it through files in `gamelab/lab/`. It reads plans (JSON) from `lab/inbox`, presses keys only while the game is in front, records the game window if asked, and writes results to `lab/outbox`. `control/client.py` hands it plans and waits for the results; `control/timeline.py` runs MapleHelper's own combo code on a virtual clock, so tests play exactly what the helper plays.

What keeps the player safe:
- **No code from plans:** it runs no code it receives; plans are data.
- **Her keys only:** it only presses the keys `config.toml` `[keys]` binds to her actions, plus `\` (key bindings window) and Esc (close windows). Enter is never pressed, so nothing typed in chat can be sent.
- **No clicks:** it can move the mouse inside the game window to hover over things, but it cannot click.
- **Game in front only:** it stops pressing keys if the game leaves the foreground.
- **Fixed at start:** it loads its code and key list once, when it starts, and loads as little of gamelab as it can (a test checks).
- **Stops itself:** it exits when `lab/STOP` appears or after 3 idle hours.
- **Plans can be cut short:** when `lab/inbox/<plan id>.cancel` appears, it stops pressing and lets go of every key it holds. A plan it hasn't started yet can be withdrawn: it renames each plan as it takes it, so the client can tell. The navigator uses this when she's hit or off course mid-plan.
- **Plans can be queued:** a plan can say how long it lasts (`end_ms`), so the next one starts the moment it ends. Keys are still all released between plans.
- **Stops on the Lie Detector:** the player checks the game screen 4 times a second, idle or not. It recognizes the countdown window (yellow "LIE DETECTOR" title), the mouse mini-game ("The Lie Detector Mini-game: use the mouse to follow the fading figure") and the Truth Booth that a failed test sends her to. When one appears, it:
  1. stops all input within about 10 ms, mid-move included, and releases any held keys;
  2. writes `lab/ALARM.json` first, then saves a screenshot (once, exiting mid-save left neither);
  3. pages whoever is at the PC with alert sounds and a Windows notification that doesn't take focus from the game;
  4. shuts down, once the watchdog has finished recording and paging.

  It never tries to answer the test. Until you run `python -m gamelab clear-alarm`, every command that sends keys or brings the game to the front refuses to run (exit code 3), including starting the player again and `probe run` (`spot`, `minimap`, `sim`, `map --offline`, `probe list`, `probe score` and the recording tools still run). When Claude is driving gamelab, it also pushes the alert to your phone.

  On 2026-10-18 the mini-game form wasn't known yet. It went unanswered, and she was sent to the Truth Booth (entry count 1). It has been recognized since then.

## Use

From the repo root, in the `maplehelper` conda env:

```bash
python -m gamelab player --elevate
python -m gamelab calibrate
python -m gamelab combo jump_back_shot --runs 4 --chain 8
python -m gamelab stop
```

1. `player --elevate` starts the player. Approve the UAC prompt.
2. `calibrate` finds her on screen. Stand her on flat, textured ground, such as a girder, with nothing around.
3. `combo` plays the combo, here 4 runs of 8 shots in a row, and reports every jump and throw.
4. `stop` shuts the player down.

Other commands (`python -m gamelab -h` lists them all):

## The mini-map

`python -m gamelab minimap` opens a window that draws the map from the game data, and on it what the stack sees and plans, as it happens (it also serves the same as a web page for a phone: see "On a phone" below):

- **Localization:** her position (yellow; a magenta ring when placed from the minimap dot because her name tag is hidden) with the way she faces and her trail, HP and MP, and how her position was worked out (rope, edge or dot).
- **Perception:** the monsters in the last look, coloured by kind, with their HP bars once hit; the drops seen on the ground (yellow), and those remembered for later (hollow squares).
- **Prediction:** where each monster can be in the next second, as the move planner sees it (red bars).
- **Motion planning:** the planned route (cyan: arcs for jumps, arrows for climbs and drops) and the chain of moves in the running key plan (magenta: where she runs, and where each move lands).
- **Attack:** where a star reaches from her (the band either side, brighter on the side she faces, cut short at a wall of her foothold group), the monsters the last throw aimed at (red rings), and the fight's last decision.
- **The tour:** its stops in order, the current one, the spot she shoots it from, the safe platforms (teal) and the hunting grounds (bright green). Below the map, the latest log lines.
- **The hunt loop** (`tour --loop`): the grounds visited, the current one and its spot; under the map, the rule that decided the last step, the objective, her EXP rate on this ground and the rate to beat elsewhere; on it, the piles in its drop store (hers bright, others' dim, expected ones small, urgent ones red).

**On a phone:** `minimap` also serves the same picture as a web page, for a phone on the same Wi-Fi, from the same process (no administrator rights; closing the window stops it too). `--window-only` starts just the window, and `--web-only` (or `python -m gamelab web`) just the page. If the page's port is taken, the window still opens (`--port` picks another). It prints two addresses: one for this computer, and one for the phone (opened on the computer, the page also shows a QR code of it). Each address ends in a key that changes every time, so nobody else on the network can watch; `--key WORD` keeps it the same, so a bookmark keeps working. The page shows the map, either the part around her (the default on a phone) or the whole of it, with HP and MP, the hunt loop's rule, objective and rates, the fight, the moves, her position and the latest log lines, as they happen. A replay (`--replay FILE`) gets buttons to pause, change the speed and jump 10 s (the page and the window each play it with their own controls). The first time, Windows may ask whether Python may accept connections: allow it on private networks. `--host 127.0.0.1` serves this computer only. Like the window, it only reads the telemetry: it sends no keys and never touches the game.

The server pushes the run's records to the page as they're written (Server-Sent Events, standard library only), and the page draws the map itself on a canvas, layer for layer as the window does, with the window's colours, reach and map (`/map.json`, from `render.py`). Her position is drawn 100 ms behind the run's clock, gliding between her positions (they come every 67 ms while she moves; ones more than 0.6 s apart aren't glided between), and the page follows a replay's pause and speed. It used to fetch the text every 400 ms and then a 40 KB picture of the map: 1.6 pictures a second, 280 ms old on average and up to 540 ms on this computer, showing 43% of her positions, for 45-70 KB/s. Measured offline on 2026-10-20 with the same live tour written again at its own pace (45 s, on 127.0.0.1):

- Every one of her 174 positions reached a client reading the stream (a Python script, on the same computer), 22-23 ms after it was written on average (p99 39-41 ms, at most 39-50; three runs).
- 2.0 KB/s, plus a snapshot of 3-10 KB when a page connects and the map (6 KB) once.
- The whole process (the server, the script writing the run again and the clients reading it) used 0.1-0.2% of a core, and 0.2-0.4% with three clients.
- In the desktop app's browser (Chromium, 3 device px per CSS px), the page drew at 60 frames a second, 0.2 ms a frame (p90 0.3 ms, at most 0.6), and only when something moved. Following the same run there for 60 s, the records reached the page 20 ms after they were written (p90 37 ms, at most 46, by the browser's own clock, which is this computer's), and its `?debug=1` corner said 22 ms (p90 37, at most 47).
- After the server was stopped and started again under an open page, the page had the new server's snapshot within a second of it starting.

A phone that was locked, or had the page in the background, catches up by itself. iOS Safari can leave a stream open but dead after the screen was locked, so the server pings every 5 s, and the page opens the stream again when nothing came for 12.5 s, or when it's shown again after more than 6 s of quiet; every connection starts with a full snapshot. Past 16 open streams the oldest ends (a phone gone from the Wi-Fi leaves one open until a write to it fails), and its page says so and waits to be shown again or reloaded, rather than come back and end the next oldest. Add `&debug=1` to the address for a corner with the frame rate, the drawing time, messages and KB a second, reconnects, how late the records come (p50 and p90 over the last 5 s; Wi-Fi adds about half the round trip shown next to it), and how long ago the newest record was written. That last isn't a delay: between moves she's looked at only a few times a second, so in five recorded live tours the newest record was over 250 ms old 30-58% of the time, with no network at all. Her position is drawn another 100 ms behind, to glide. `&delay=0` draws her where she was last seen instead of gliding. `/frame.jpg` (the map as a JPEG, `?view=her` around her) and `/state.json` (the text) are still served for a quick look, but the page doesn't use them. WebRTC was left out: the server would need aiortc and FFmpeg's libraries, for a stream of 2 KB/s on a home network. Not tried on an iPhone yet.

Hunting commands (`hunt clear`/`kill`, `nav`, `tour`) record what they see and plan to `lab/telemetry/<time>-<command>.jsonl` (`gamelab/telemetry.py`). The window follows the newest of those files, so it can be opened before or during a run. Live, the window never takes focus from the game: the player only presses keys while the game is in front, and screen captures see whatever is on top. So it goes beside the game window when the screen has room, and clicks on it don't activate it. A replay (`--replay FILE`, also last night's `lab/sweep_track.json`) is an ordinary window: space pauses, + and - change the speed, and the arrow keys jump 10 s.

## Offline: the simulator and golden traces

`gamelab/sim` is a small game that the whole stack runs against, with no game and no key player. `FakeEyes` answers perception's questions from a simulated world, and `FakePlayer` runs key plans on it on a fake clock. Her body moves as the engine moves her (`motion/body.py`, below, which the planner's constants come from): the game sees each key a measured lag after it goes out, an arrow speeds her up and letting go brakes her, a jump gets the kick, the opposite arrow brakes her in the air, and an attack stops her landing; she climbs as measured. Monsters walk their platforms, touch her (half of the touches are evaded, as measured), die from stars, give EXP and drop loot. An attack picks its target when it starts, about 67 ms after its key, from where she is then (as in game; see Attack): on the ground the claw swipes a monster on her level whose body its swing reaches, else the star goes to the monster the star's search picks, band by band; from a jump, to the nearest whose body reaches into the attack's area. The bodies are as tall as the game data has them walking (taller for 0.6 s after a hit, while they flinch). So her jump-throws go over snails as they do in game, and from the ground a star goes over a monster right under her. 66 scenarios cover navigation (every kind of move, monsters in the way, fighting on the way, cut-off plans), single moves, fights (a snail cornering her on a short platform too, a step wall between her and the monsters), kills, mop-ups, a full inventory, tours and rests (with and without the fighting escort), the hunt loop (`loop_*`: the basin, a spot off the ground, leaving an empty ground, lull loot, a rest, 8 minutes end to end, the game's errors, another player), and the in-game probes (`probe_*`: the window's top from 13, the step wall from 4 from the ground and jumping back, jump throws at a snail).

- `python -m gamelab sim tour_run --speed 4` runs a scenario and records it for the mini-map: open `python -m gamelab minimap` first to watch it as it happens.
- `python -m gamelab.analysis.physics_check` replays her recorded movement (18 recordings, or the 6 kept as test fixtures) through the physics models and prints how far each is off (see Motion planning).
- `python -m gamelab.sim.golden check` reruns every scenario and compares it with the golden trace recorded earlier: every key plan, log line and result. A refactor that leaves those byte-identical hasn't changed what she does. `record` rewrites the traces (after an intended change). The traces hold map data, so they stay in `lab/golden` (git-ignored).

The move into the layers above was checked this way: all 50 traces stayed identical, apart from two counters that were never read (`Report.out_of_reach`, `Hunter.skipped`), which were removed.

**Comparing policies** (`python -m gamelab.sim.harness`): `run POLICY` hunts 20 simulated minutes on each of 10 world seeds (`tour`, `loop`, or `loop-avoid`), and `compare BASE CAND` applies the bar seed by seed: more EXP a minute on 8 of 10 seeds and none more than 10% worse, at least the drops share, no more HP lost, no death. What a run gave is read from the simulated world, not from her own reports. Preset `game` adds the game's errors (27.5% of stars miss, hit monsters hidden for 1-3 s, 10% of looks miss a monster, her lags spread as measured), 60% of spawns filled, another player killing a monster every 25 s, and 60 potions; `plain` is the simulator's own crowded world; `--think 1` also charges the stack's real computing time to the clock (those runs aren't repeatable). `rests` compares trips to rest at low HP with and without `--rest-avoid`. Runs are saved in `lab/harness` (git-ignored).

Tests can't press keys, page anyone or write under `gamelab/lab` (`tests/conftest.py` stops them), and the simulator refuses to run unless its fakes are in place.

## Perception

| Piece | Does |
|---|---|
| `mobs.py` | Finds snails, slimes, pigs and Orange Mushrooms. It matches each monster's body-colour silhouette first, then checks the best spots with masked colour templates. About 100 ms for the fight's band around her, 300 ms for the whole screen. The first pass ignores windows with almost none of the monster's colour: their normalised score is noise that can reach a perfect 1.0. The frame is also cut to an even size so the half-size mask is an exact shrink. An odd size (the fight's band was 151 rows) smeared faint colour into blank windows. In the basin, those fake matches took all 12 checks per monster type, so the fight never saw the snails and pigs at her level while a whole-screen look did. That's likely also why one pass over the whole screen once missed three slimes in plain view; whole-screen looks still go band by band. |
| `sprites.py` | Templates for the monsters on the current map, made from the game's own sprites (every stand, move and hit frame) at their on-screen size. They're added to the screenshot cut-outs in `assets/mobs/`, which still catch monsters half hidden in plants. Built on first use and kept with the other extracted data (git-ignored). |
| `loot.py` | Finds drops on the ground: what this map's monsters drop (Squishy Liquid, Slime Bubble, Leather, Pig's Head, Pig's Ribbon, Orange Mushroom Cap, Snail Shell), the potions monsters this level drop (Red, Orange, White and Blue Potion), and bronze and gold mesos (3 spinning frames each). Templates are the game's own item pictures at their on-screen size, scaled by their opaque pixels only. A spot counts when the masked template matches (0.6) and its colours differ from the template's by at most 24 on average, checked where the picture covers whole pixels. The sea and island backdrop matched the Blue Potion's shape at 0.60-0.63, and UI buttons the White Potion's; they differed by 27-57, real drops by 12-19. Only a strip just above each platform is searched (drops lie on the ground), on 4 threads: about 30 ms for her platform, 140 ms for every platform in view. On 110 saved frames it found all 18 drops and nothing else. Drops lay on the ground about 2 s after her EXP went up, and monsters are drawn in front of them. |
| `nametag.py` | Her name tag, matched at full resolution (at half size the score swings between ~0.6 and ~0.9). Of the good matches in the play area, the one nearest where she was wins: her name also shows in the minimap, the bottom bar and the party list. |
| `hud.py` | HP and MP from the bar colours; her EXP number, which only changes when she gains EXP; a monster's HP bar; the purple MISS or damage numbers when a monster touches her. |
| `minimap.py`, `terrain.py` | Her yellow minimap dot; the ground under her; ropes and ladders on screen. |
| `lie_detector.py` | The Lie Detector's three forms (see above). |

## Localization

Her position comes from the minimap dot, which is always visible. The minimap is the map at 1/16 scale shown 1.40625× larger, so one minimap pixel is 11.4 map units; the dot is snapped to the platform she's standing on. With her name tag on screen, her x is refined from a rope in view (ropes are drawn exactly at their map x) or the visible end of her platform. Her place on screen comes from her name tag. When the tag is hidden, for example behind the party HP box at the map's edge, it comes from the dot and the camera instead: the camera keeps her at a fixed spot on screen except near the map's edges, where it stops, and it learns that spot from the looks where the tag is visible.

The map model (`mapdata.py`) comes from the game's own data, read with `gamedata` and kept off git: platforms (footholds joined end to end), walls, ropes and ladders, portals, monster spawns, EXP per kill, each monster's body (from the boxes of its frames: how tall it is at least while it stands or walks, how tall while it flinches, how wide, and from its die1 frames how long it's seen dying; `monsters.bodies`) and the minimap's scale, in map units (the screen shows them 1.40625× larger at 1920×1080). Each foothold keeps its group, as the map image files it (`foothold/<layer>/<group>/<id>`, `Segment.group`): a floating block is one group, its floor and the walls hanging from its ends; steps joined by a wall share one (platforms 2 and 4, and the basin's 34, 35 and 36). The game's collisions in the air go by it (Motion planning), and so does what stops a star (Attack). And each keeps whether the game lets her drop through it (`forbidFallDown`, `Platform.no_drop` and `drop_ok`): 14,197 footholds in 51 of the 306 map images forbid it, none on this map. A platform's footholds almost always agree (of the 2,100 platforms on those maps, 1,340 forbid it all along, 757 nowhere, 3 in part). No drop is planned through one (`route`, `flow`), and in the simulator ↓ + jump on one does nothing, as on the bottom floor.

A monster seen on screen goes on the platform its kind spawns on: feet read from the screen can be 20 units off, which once put pigs "on" the safe platform above them, and she backed away from them and off it. It's kept within that platform's ends: read from the screen one can seem up to 25 units past an end, and past the step at the end of platform 2 it would seem in front of the wall it's behind. From look to look, a monster is the same one when it's the same kind within 85 units; the move planner also tracks which way each walks and how fast (`Tracker`), to tell where it can be next.

## Motion planning

| Module | Does |
|---|---|
| `body.py` | How the game moves her: the one movement engine. One step on the ground and in the air (`ground_step`, `air_step`), the jump's kick (`takeoff`), the lags (`Lags`), closed forms on flat ground for planning (`run_x`, `run_time`, `stop_distance`, `hold_for`, `jump_window_ok`), flights over a map (`fly`, with the arrow held and her speed as she lands) and a key timeline replayed on flat ground (`replay`). | `physics.py` | Her jump (`jumpSpeed` 555, gravity 2000: 77 units high, 555 ms in the air) and fall, and where a jump or fall lands, simulated against the map's platforms and the walls of the foothold group she leaves (`group`: below), with her sideways speed as she lands (`flight`). The step-up probe brackets it: from 4 at 2 (a 60 step), jump throws (the line 26 higher) stopped and jump backs (44 higher) getting through would put it at 16-34. On this map it rules out one pair of platforms, 4 -> 2 (at every x), and nothing else; 174 of the 306 maps have steps within one group. She doesn't throw at a monster behind such a wall, or walk along her platform for one, spots don't count what's behind one, and a kill isn't matched to one. A monster's x is taken 1 unit inside its platform's ends, so one at the foot of a wall rising from its own platform's end (the basin's sides) isn't behind it. `reach.WALLS_BLOCK = False` switches the rule off: the probes that measure it do so for their run (`probe run step-up`, `step-down`, `hanging-wall`); the shot log and the probe log record its verdict either way.
- **A group** (`stance.py`): a star hits the nearest monster in reach on the side she faces, so she throws toward the side with the most monsters in reach, and keeps working the side she faces while it has any. Turning after every throw spread the damage over both sides.
- **What an attack hits is picked when it starts** (`reach.in_area`), about 67 ms after its key like a jump's lift-off, from where she is then; the star that flies is only a picture. From the ground, the claw's swing comes first, then the star's search (above). From a jump, it's the nearest monster whose body (`localization.monsters`: the boxes of its frames in the game data) reaches into an area fixed to her feet: from 19 below them (fitted, 18-21) to at least 60 above, its near side within 400 ahead. A jump throw's attack key used to come 100 ms after the jump key (the macro's F1 combo), so she was 42-49 units up when it started (60 fps recordings), and the area's floor was about 30 above the platform: over a snail, which is 24-26 tall (33 while it flinches); slimes (40 at least), pigs (38) and Orange Mushrooms (55) reach into it. On 2026-10-19, of 45 jump-throws at snails 3-77 units away on the 168-unit platforms 3, 20 and 22, at most one hurt the snail, and pigs, slimes and Orange Mushrooms on the platform 60 above took the stars and died. Their EXP was taken for the snail's ("snail down"), and the snail, still alive, was then left alone as a dying one. Now the key comes 40 ms after the jump (`physics.JUMP_ATTACK_MS`): the attack starts about 26 units up, and the area's floor about 7 above the platform. In game on 2026-10-20, at a snail 20-60 units away on platform 22: keyed 100 ms after the jump, the star flew over it and did nothing; keyed 40 ms after, a star hit it for 78 and killed it. In a hunt loop afterwards, jump-throws at snails killed them.
- **Too close:** she jumps away from it, turning toward it in mid-air to throw. A star leaves about 520 ms after the attack key, in the air or not (recorded at 60 fps), so the key goes in right after lift-off (85 ms after the jump key) and the star leaves just as she lands; its target, though, is picked when the attack starts, about 40 units up and 16 out (`jb_k165` at 60 fps, the jump keyed 80 ms after the arrow; about 25 out by the engine with it keyed 130 ms after, as now), not the whole jump away. It needs 110 units of room behind her and no monster within 160 there; otherwise (cornered) she throws from a jump straight up. Each only if that attack starts low enough to pick the nearest monster's kind (`reach.air_hits`: how tall it is at least, 6 units into the area): a jump back's (floor 25 up) can't pick a snail, so cornered by one she jump-throws (floor 7 up); with room behind her she steps back to 3 past the claw's edge if she can (`reach.star_sure`: 124 for a snail; a star from the ground). A monster counts as too close by its size, as far as the claw would swipe it (`stance.close_to`; the hunt loop's close quarters too). It all follows from `JUMP_ATTACK_MS`: keyed 100 ms after the jump, a jump throw's attack couldn't pick a snail either, and she shot it from the ground (the claw swipes it, weak but always hitting: 5 swipes kill one). Under a platform within her jump height she doesn't jump to attack (on platform 20, five jump-throws at a snail put her up on 19); she steps away instead, or (cornered) throws from the ground.
- **Spacing:** she steps away from any monster on her own platform within 110 units, or as far as the claw would swipe it (a pig within 136), unless that walks into another one or off her platform. With monsters on her platform she stays 50 units from its ends: a monster touching her pushes her 20-21 units on a wide platform, and 82 and 109 units on a narrow one, which knocked her off.
- **Facing:** she only taps an arrow to turn when she isn't already facing the target. Every tap also walks her a few units, and nine taps in a row once walked her off the end of her platform. A jump-throw that turns her first waits for the tap's walk to stop (`actions.JUMP_THROW_TURN_MS`), so it goes straight up.
- **Where to shoot a platform from** (`spots.py`): a spot on another platform she can stand on, either one no monster can reach or one only monsters not worth hunting reach (snails: she shoots those when they come close), with at least 30% of the hunting platform in reach. Of the spots about as good as the best, she takes the nearest: coming up from the basin she shoots 21, 18 and 12 from the platforms below them, and from above she shoots down.

## Control

- **Actions** (`actions.py`): every key plan she sends, blocking until the player has run it. Throws come one per attack cooldown. Whenever she walks, she presses pick-up every 0.15 s; on a kill's drops she stops and presses it 4 times (a press takes one item, a pig drops several).
- **One move at a time** (`mover.py`), closed loop, for what a chain can't predict, such as climbing down a rope, which needs her lined up on its top. Also gets her off a rope she's hanging on.
- **A route** (`navigator.py`): one look, then plan, then chain as many moves as are safe and predictable into one key plan. Like a player, she doesn't go the same way every time: each trip weighs every move by a random 1 to 1.35, and moves start from varied spots. From platform 1 down to 34, 14 different routes came up in 40 trips, all within 1-2% of the quickest. Chains are capped at about 3.5 s, and the next one follows on without a stop where it can:
  - About 0.9 s before a chain's last landing she looks around (from where she starts, where she's going can be off screen). With an escort, what would stop her where the chain ends stops her there: the trip's `until`, or in hunt mode a monster in reach.
  - Once she's back on the ground for good, a look places her (standing: ground under her feet, not just her minimap dot, which put her on a platform she was still falling past), the next chain is planned from there (about 5 ms) and queued, and the player starts it the moment the running one ends. The running plan keeps her going for the ~0.3 s that takes: running on with the arrow held, short of the next move, or standing. That look skips the monster search (in game 110 ms, 131 at p90, against 205 with it): with it, none of 15 chains in a hunt loop followed on (seen too late to plan in time); without it, every one with room to run on did. Where there's no room for that (she lands right before her next jump, as all the way up the staircase from 34), she stops there instead; and when nothing follows after all, the rest of that run on is cut, so she stops where the chain was to end.
  - Planned from where the running chain was predicted to end instead, errors built up: a landing 12.5 units off made the next running jump leave 12.5 units early, and landing late (still in the air, or sliding to a stop once her plan was over) the next chain's keys came too early and she fell off.
  - With an escort, chains are planned without the monsters (it fights them instead, at the stops), so one follows on only where none of the monsters seen can get near it, and none stands in the way of its first move; the run on past a chain's end is checked against them too.
  - Where she stops, the look the next pass needs is taken once she has stopped sliding (0.35 s at most): it used to be two looks in a row there, about 0.4 s standing (0.6 s with the slide). A trip also starts from its caller's last look if no key plan was sent since (`go(scene=...)`): the hunt loop's decision goes straight to the first chain.
  - In game on 2026-10-20 (a 3-minute hunt loop): the stops between chains were 0.2-0.5 s, against about 0.4 s the day before, and 0.75-0.8 s with the slow look. Most chains on this map still end where she lands right before her next jump, with no room to look first, and stop there.
  - In the simulator, over 164 paired trips per case: without monsters, trips took 11% less time in transit and 15% less avoiding monsters, with misses from 20 to 9 and from 68 to 10 (the queue that followed on from predicted ends was most of those). With monsters the differences are within the noise: hunt mode 3% faster, avoiding 2% faster, transit 7% slower (one standard error), with as many misses and hits as before.

  Meanwhile it glances at her minimap dot and HP about 15 times a second: a hit, or her standing on a platform the running leg doesn't go to, cuts both plans short, and it replans from wherever she is. Without an escort she avoids monsters: a leg a monster could walk into costs extra so a way around is taken, else she waits for it to move off. With an escort (hunting tours), she fights instead (see Behavior). If her minimap dot disappears, for example under another program's tooltip, it moves the mouse inside the game to clear it.

## Behavior

- **The ledger and the drop store** (`ledger.py`): every EXP gain is a kill, placed on the monster that was first in the path of one of her throws in the last 2.5 s, in the order the attack takes them (the claw's swing, then the search's bands; preferring one that has gone). A placed kill's drops become an expected pile there, and looks that searched for loot confirm or forget piles; a pile no kill of hers explains is someone else's.
- **The hunt loop** (`hunt.py`, `tour --loop`): instead of the tour's stops, loot trips and fights on the way, one decision after every look, by the first of these rules that applies: close quarters; back to the high ground; an urgent pile (about to vanish, close); shoot what's in reach; in passing (while travelling, 15 s per platform); a pile on her platform; a better spot; lull loot (nothing left on the ground and her kills due back); wait; and, leaving, the piles left then and the next ground. She leaves a ground by the rate rule: her EXP rate there below 80% of the best other ground's (the trip there included), or nothing left and nothing due back (the fast exit; that ground is skipped for 2 minutes). Objectives (a spot, a pile) are suspended by higher rules, not ended, and dropped after 60 s, suspensions included. Visits are recorded with their length in `lab/grounds.json`. The numbers are guesses tuned in the simulator (`docs/hunt-modes.md`).

- **The hunter** (`hunter.py`) keeps count after every look, whoever took it: a kill counts only when her EXP number goes up (counting a vanished target as dead was wrong about half the time: hit monsters flinch and hide behind damage numbers, and other players kill monsters too). It drinks an HP potion below `--potion-hp` and hands control back below `--low-hp`.
- **A fight** (`fight.py`, `clear`): one throw per attack cooldown, with a look during each. She never walks past a monster. A monster of any kind that comes close on her own platform is in her way and fought, snails included. Reaching a stop's kill count doesn't end a fight while monsters are still in reach. An EXP gain seen by a look the fight didn't take itself (a sweep's, before it ended at its kill count or in the sweep after it) or by the look it ended on (knocked off) is still told apart as a kill when it ends. On a tour she also shoots monsters worth hunting on any platform in reach. A star hits the first monster in its path, whatever its kind, so kills are matched against everything in the path, not just what she was aiming at: from the ground what the claw or the search can pick by each monster's body (`reach.ground_pick`: not a slime 60 below and 150 off, nor a pig 440 off); from a jump, as high as she is when the attack starts (`reach.in_area`): monsters on the platform above count as far as a star reaches, a snail beside her doesn't. A monster just hit (its HP bar new or lower since it was last seen, or hidden under its damage numbers) counts as tall as it flinches (the game data's `hit1` frames, for 0.6 s): a pig 60 below her is then in the path from 111 units along, against 151 walking.
- **Hidden monsters:** a monster she was throwing at is still thrown at for 1.8 s after it drops out of sight (hit, it flinches under its damage numbers, and the detector loses it for 1-3 s). A kill is still seen fading out where it died as long as its death animation runs (the game data's die1 frames: a pig or an Orange Mushroom 0.66 s, a slime 0.84, a snail 1.26), and what's seen there is left alone that long from the look that saw her EXP go up (`fight.fade_s`; 1.2 s for every kind before, and for a kind the data lacks).
- **Waiting:** with nothing in reach she walks just close enough to the nearest monster. With monsters seen but out of reach, she waits up to 2 s from a safe platform (1 s on the hunting platform). With none seen at all, she moves on after 0.4 s.
- **Fighting on the way** (`FightOnTheWay`): before each move, a short burst at whatever a star reaches from where she stands, on any platform: up to 3 kills, never walking after them, up to 5 bursts per platform. It also shoots any monster in the way of a move along a platform. It's turned off while she goes to rest.
- **Loot** (`looting.py`): each kill's drops are swept when the fight is over, if they fell on her platform (it looks again until she has landed: the fight often ended mid-jump). After the sweep she looks again and goes back for drops still on her platform, standing right on each one, for up to 3 looks. Drops elsewhere are remembered for the tour: her kills', and any seen on other platforms. A remembered spot is forgotten only when two looks 1.5 s apart, 3 s or more after the kill, both see it empty. A drop she has stood on twice that's still there is left alone for 90 s: for mesos that means someone else's drop; for an item it may mean her inventory is full, which the pickup log (OCR) says, or 3 such items in a row. With it full she leaves items and still picks up mesos.
- **A tour** (`tour.py`) sweeps every platform worth hunting. A platform's worth is the EXP a visit is expected to give: at first 30% of its spawns' EXP (game data), counted as 2 visits, then blended with what each visit really gave (`lab/grounds.json`). Monsters giving under a quarter of the map's best EXP aren't hunted, only shot when in her way (snails give 2, against 12-15). Platforms expected to give under 15% of the best one's are skipped: by the data, 34 and 35 spawn slimes, but 11 visits found only snails there. The order: nearest next by route time, judged with a random ±25%, then tidied to cut travel (2-opt); after each stop the rest of the sweep is planned again from wherever she ended up. At a stop she kills all she can reach from her spot; if some are left out of reach, she moves to another spot that reaches them rather than walking down into them, and only then collects the drops (nearest by route first; drops of monsters shot on the way are kept for the next collection, and none starts a trip after 180 s). She moves on once a whole-screen look sees no monster left. When HP is low, she rests on the chair at the nearest safe platform (on the way there she still drinks potions, but low HP doesn't stop the trip), and she ends standing by there.

**How a probe throws:**
- The navigator takes her to her place, keeping clear of monsters, and she keeps to it: knocked off, or carried off by a jump back, she walks or goes back.
- She throws the regular attack only when exactly one monster is in front of her (within 420 units by its middle, from 140 above her feet to 140 below), and it's one the probe throws at, in range sideways. `--crowd N` also throws with N others in front, for a busy ground.
- After each throw she waits for its star's evidence before the next: every look until 0.9 s after the star was due, or up to 2.5 s while the target is hidden under its damage numbers. So a hit is never another throw's, and a monster hit by one throw has stopped flinching when the next attack picks.
- A monster of a kind it doesn't throw at that comes close on her platform is fought off first.
- `--x`, `--dx LO-HI`, `--style` and `--throws` change a probe. `--walls on|off` sets whether her decisions keep to the wall rule during the run (who counts as in front, and the fights); the probes that measure it set it off.
- The player, the Lie Detector watchdog and the alarm work as for `hunt kill`: `probe run` is refused while the alarm is up, and every key goes through the player. Waiting for a lone monster she can go minutes without a key, the moment the alarm is otherwise noticed, so the probe also checks it before every look (a look brings the game to the front). `probe list` and `probe score` send nothing.

**The log** (`lab/probe_geometry.jsonl`, one line per throw) keeps where she and every monster in front of her were at the throw, and at the first look after it (about when the attack picked its target). For each of those monsters it keeps its HP bar before the star could land, the bar in every look after, the looks it wasn't seen in, and whether it was gone at the end. It also keeps her EXP gains and the wall rule's verdict.

**`probe score`** (or `probe score FILE`) reads the log with the map's game data. A monster showed a hit when its HP bar came up or dropped, or when it died (her EXP up, and it the one gone). It showed none when it was seen with its bar as before 0.3 s or more after the star was due. While it was hidden, nothing can be told. Then the scorer fits:
- `SEARCH_TOP0` and `SEARCH_FLOOR0`, to the throws from the ground. For each value it finds the monster the attack takes (the claw on her level first, then the search's first band, the nearest in it, at the pick), scored by likelihood with the two hit rates fitted. A monster taken shows a hit at least 30% of the time and one not taken at most 20%: without those bounds, a run of hits fits "not taken" as well as "taken". It prints the values that fit (within 1.92 of the best), and how reach's value and meowdb's 44 do.
- What stops a star, over every throw: the rule, no walls, every wall, and a line from her to the target's feet; and the range of `SHOT_H` that fits (a jump raises the line by `reach.air_rise`).
- Between her level and 60 below her: the search alone against the old ramp.
- From a jump: the area against the search, from as high as she is and from the ground she jumped from.
- The claw probes: the target's hits by how far off it was, each the claw's (it took under 15% of the bar) or a star's.

## Limits

- **Recalibrate** after moving the game window, changing maps or changing resolution. Her name-tag template is kept between calibrations; `calibrate --fresh` rebuilds it, and should be run where no rope crosses her name.
- **`hunt` needs a 1920×1080 game window,** the size its templates were made at.
- **Each new monster type needs a colour gate** (a body-colour test in `PALETTES` in `perception/mobs.py`) before its game sprites are used. Its templates come from the game data automatically.
- **Her name tag can be hidden** behind screen widgets at the map's edge, like the party HP box. She's then placed on screen from the minimap dot and the camera, which is only good to about 11 map units.
- **Camera correction for recordings needs ground with a pattern** under her, like a girder or tiles. Plain ground can't be tracked.
- **Swing detection is tuned to the claw's white/lavender swing effect.** Other weapons or skills may need `SWING_MIN_PIXELS` in `analysis/track.py` adjusted.
- **Lucky Seven costs about 7 MP per cast.** A 32-shot test uses about 220 MP. Use `--regular-attack` for long runs. Hunting uses the regular attack unless `--skill` is given.
- **How far above or below a star reaches** beyond 60 units isn't measured. `hunt shots` sums up the shot log.
- **Other players** hunt this map too. Platforms are often empty, and stops then end with no kills.
- **EXP from anything else** counts as a kill if it comes just as a target vanishes. In a party, that includes EXP shared from other members' kills.
- **Loot templates cover this map's drops only** (`ITEMS` in `perception/loot.py`); another map needs its drops' names added. Equipment, scrolls, and bills and sacks of mesos aren't looked for; she still picks them up when she walks over them.
- **The full-inventory message** is "You can't get anymore items." It's in the client, not the data files, so `loot.py` matches that and the usual other wordings. Without the OCR packages, only the 3-in-a-row rule tells.
- **The simulator is a model:** its timings and physics are fitted to gamelab's own measurements, its monsters only flinch taller (they aren't pushed back by hits), and its perception is exact unless a scenario adds noise. Use it to check that a change does what was meant, then confirm in game.
